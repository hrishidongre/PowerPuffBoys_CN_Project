What we built, in one paragraph

Four laptops on the same Wi-Fi, pretending to be a small company's servers. Someone types https://app.powerpuffboys.test in a browser. Our own DNS server tells them which machine to go to. That machine is nginx, which handles the encryption and then quietly passes the request to one of two application servers behind it. The person in the browser never knows there are two servers, and never learns their addresses. Phase 1 built that. Phase 2 makes it keep working when parts of it die.

The one answer to rehearse: what happens when you press Enter

If you can tell this story, you can answer most of the paper. Six steps.

1. The name has to become an address

Your Mac does not know what app.powerpuffboys.test means. It asks the DNS server it was told to use, Adi's Mac, over UDP port 53. Adi's machine replies "that name is at 10.7.17.226". Nothing has connected to anything yet. DNS is a phone book, not a phone call.

2. Open a connection to that address

Now your Mac opens a TCP connection to 10.7.17.226 on port 443. Three messages, the handshake: SYN, then SYN-ACK back, then ACK. Both sides are now sure the other can hear them.

3. Agree on encryption

Inside that connection, TLS starts. ClientHello, ServerHello, the server sends its certificate, keys are exchanged, Finished. Our certificate is signed by our own small authority, "PowerPuffBoys Local CA", which every Mac has been told to trust. From here on everything is encrypted, and Wireshark shows only "Application Data".

4. Ask for the page

Only now does the actual HTTP request go out: GET /api/status. It is inside the encrypted tunnel, so nobody on the Wi-Fi can read it.

5. nginx decides who answers

nginx decrypts the request and forwards it, as plain HTTP over our trusted LAN, to Hrishi's Mac or Vedant's Mac, alternating. This is the only unencrypted hop, and that is deliberate: encryption was already done at the front door, and the LAN behind it is ours.

6. The answer comes back

The backend replies with JSON and an X-Backend: A or B header. nginx sends it back down the same encrypted connection. Run the request ten times and that header flips between A and B, which is the proof that load balancing is real.

Three things people get wrong

  • DNS does not connect you to anything. It only hands back an address. If DNS breaks, the address still works if you type it directly.
  • Encryption stops at nginx. The hop to the backends is plain HTTP. If asked why, say: it was already encrypted to the edge, and the backend network is private and trusted.
  • The client never knows the backend addresses. That is the point of a reverse proxy. We can add, remove or move backends and nobody outside notices.

The one honest weakness, and they will ask

Vetri's Mac is a single point of failure. Both backends can be healthy and the service is still dead if the front door goes down, because everything flows through it. To fix it you would need two front doors sharing one address: two DNS records pointing at both, or an address that can move between them, or another balancer in front of the two. Extension E is us doing that move by hand.

If it breaks: always go bottom up

A problem low down makes everything above it look broken, so never start at the browser. ./phase2/troubleshoot/diagnose.sh walks all five in order and stops at the first failure.

Viva questions and short answers

Walk me through one request.

The six steps on page 2. Name the protocol and port at each step.

Why does the client never know the backend addresses?

Because it only ever talks to nginx. That lets us move, add or remove backends without telling anyone, and it means the backends can be firewalled off completely.

Where does TLS stop, and what is unencrypted?

It stops at nginx on Mac 2. The hop from nginx to the backends is plain HTTP over our own LAN. That is normal practice when the internal network is trusted.

What is the difference between DNS failing and a server failing?

If DNS fails the name does not resolve, but typing the address still works. If the server fails the name resolves perfectly and then the connection or the request fails. One is the phone book, the other is the phone.

What does the TTL do?

It is how long a client is allowed to remember an answer. Ours is 30 seconds, so after we change a record, clients keep using the old address for up to 30 seconds before asking again. That is exactly how real services move traffic between machines.

Why is closing a TCP connection four messages when opening is three?

Opening is three because the server's "yes" and its own "are you there" fit in one message. Closing is four because each side shuts down its own direction separately, and the server may still have data to finish sending after the client says it is done.

Why do repeated requests sometimes return 304 instead of 200?

The first response carries an ETag, a version tag. The next time, the client sends that tag back and asks "has it changed?". If not, the server replies 304 Not Modified with no body, which saves the whole transfer. A fresh cache hit is different again: the client does not ask at all because the Cache-Control: max-age=60 has not expired.

Our two backends have different ETags. Does that matter?

Yes, and it is a good thing to notice. If you cached from A and then revalidate against B, B does not recognise the tag and sends a full 200. That is what happens when you load balance without sharing cache tags between servers.

What is still a single point of failure?

The nginx machine. See page 3.

Which layer is Ethernet, IP, TCP, TLS, HTTP?

Ethernet is the link layer, IP is network, TCP is transport, TLS sits above transport, and DNS and HTTP are application. DNS is the odd one out because it uses UDP, not TCP.
